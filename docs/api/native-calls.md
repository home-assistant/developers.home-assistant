title: "Native call providers"
---

:::note Proposed contract
This contract accompanies experimental Companion and frontend changes. It is not available in released apps merely because an integration implements it. Android is the reference implementation. iOS requires its own CallKit and push implementation and has not been qualified by the Android tests.
:::

A call provider is a Home Assistant integration that owns routing and call state. Companion supplies the portable device's native communication audio and operating-system call controls. A provider may use SIP, another WebSocket service, or its own media backend. Companion does not need to implement those protocols.

## Discover a compatible app

Compatible registrations advertise `app_data.native_calls: 1` through `mobile_app`. Bind a phone to the stable registration and authenticated user, not to the model name or user agent. A display-name change must not create a new phone.

## Incoming call

Use the addressed mobile_app notification service with `message: command_call`. Its data contains `call_action: ring`, `call_id`, and `call_path`. The call path is an authenticated `/api/` path on the registered Home Assistant server. It identifies one call generation.

Companion reads the descriptor before presenting the invitation. GET returns `id`, `state`, `caller` (the remote party's display label), `direction`, `remaining_ms`, and `media_path` when available. The provider must validate registration ownership, the selected endpoint and the live generation. A terminated or superseded call returns HTTP 410.

`remaining_ms` is nullable. A positive value is the remaining unanswered-call deadline owned by the provider; zero means expired. `null` means no additional deadline. Companion must not invent a default ringing limit or apply this deadline to an established call.

POST to the same path accepts `answer`, `decline`, or `hangup`. Answer includes `client_id`, a media-owner identifier generated by Companion. It is not an authorization credential. An answer response with `state: in_call` and a media path means the provider's connection has completed, not merely that an answer command was queued.

Send `call_action: cancel` for the same identity when ringing or the call ends. Duplicate invitations and delayed commands for another generation must not affect the current call. Platform presentation and provider state are separate lifetimes and both must be released.

## Audio transport

The current transport is authenticated WebSocket PCM. The media URL is on the same registered server; redirects to another origin are rejected. `client_id` identifies the owner of the media attachment.

Text messages negotiate `tx_format` and `rx_format`, encoded as `sample_rate:s16le:channels:frame_ms`. The direction is relative to the app: transmit means microphone audio sent by Companion. `audio_direction` uses `sendrecv`, `sendonly`, `recvonly`, or `inactive`. `remote_connection_held` suppresses media while held.

The reference adapter also accepts optional `audio_mode`, defaulting to `full_duplex`. Its `mic_only` and `speaker_only` values describe the remote endpoint and constrain the complementary local path. Providers with explicit direction negotiation can leave it at the default.

Binary messages start with byte `1`, followed by signed 16-bit little-endian PCM. A message must fit within 4096 bytes. Negotiate supported rates and frame sizes before allocating audio resources. Queue capacity is bounded. After native audio resources are ready, the app sends `{"type":"audio_ready"}`.

A negotiated 48 kHz stream does not guarantee that every physical or Bluetooth audio route runs at 48 kHz. Report transport format and physical route measurements separately.

## Platform and delivery requirements

Android uses Core-Telecom, communication audio, runtime microphone permission, and call notifications. The provider must not manipulate Android audio routing through a second independent mechanism.

Local notification delivery and Firebase remote wake are separate qualification cases. A foreground emulator test does not establish behavior under battery restrictions, cold remote wake or every Bluetooth route. HTTP on a local test server does not qualify browser microphone access over a LAN; browser media normally needs HTTPS or a secure localhost context.

An iOS implementation must report genuine VoIP pushes promptly to CallKit and coordinate audio activation with AVAudioSession. Android's fetch-before-ringing flow cannot simply be copied into a PushKit callback.
